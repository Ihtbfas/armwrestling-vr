# P0｜接管同学 VR 工程、导入 GitHub、先跑通现有场景

> 状态：**2026-11-18 已完成本轮接管及主场景离线 Editor Play**。本任务书保留为验收依据；实际结果、未通过项和后续建议见 [P0 交接](../P0-handover-result.md)。参考架构见 [../architecture-reference.md](../architecture-reference.md)，不是强制实施清单。

## 项目目标

将用户已经收到的同学 Unity/团结 VR 工程作为真实起点，在不无谓重建的前提下完成：

1. 保留可恢复的原始工程，检查项目版本、可运行场景、所需 SDK/资源，形成简短“已实现功能清单”；
2. 在 Windows 上使**原有有意义的 VR 场景尽可能正常打开、进入 Play**，解决主要编译、缺包或资源问题；
3. 将确认可以公开且实际需要的 Unity 项目文件导入独立仓库 `Ihtbfas/armwrestling-vr`，留下可复现运行步骤；
4. 找出后续 P1 单自由度机械角度映射最值得先处理的问题。

## 可自主决定的部分

- Codex 可以调查项目结构、选择保留/调整目录、修复直接影响运行的编译和包问题、重用已有场景或 Prefab、自行迭代测试，无需每次小修改前询问。
- 允许为清晰和可维护性做少量必要整理；允许用简单、可读的 C# 脚本补足缺失入口或演示逻辑。
- 可以根据实际包依赖和版本使用 Unity/团结原项目所需编辑器，不预设与历史 `UnityUdpDemo` 测试工程相同。
- 遇到可解释、可控的非关键警告不必无限追查；优先交付运行基线。

## 必须守住的边界

- **原工程优先。** 不因为想建立“理想框架”就重建人物、动画、桌面和所有场景；保留原始备份/导入基线。
- 保留 `.meta`、GUID、Prefab/Scene 引用。资源移动尽量在 Editor 内完成；必要的批量文件移动必须同时处理 `.meta`，并检查引用。
- 当前本仓库仅负责 VR。控制系统仓库：https://github.com/Ihtbfas/armwrestling；UDP V0.1：https://github.com/Ihtbfas/armwrestling/blob/main/docs/vr-udp-v01.md 。本阶段不修改外部协议、人物阻力策略和 STM32 代码。
- 公开仓库不得上传未获许可的第三方或同学素材；不自动推定 MIT 覆盖所有外部资产。原有 Unity 插件与 SDK 的许可证和来源需简单确认。
- 不提交 `Library/`、`Temp/`、`Obj/`、`Logs/`、`Build/`、`UserSettings/` 等可重建缓存；按项目实际位置使用 `.gitignore`。对大模型/纹理等二进制资源酌情采用 Git LFS 并检查仓库限制，不要无条件纳入大文件。
- 如未真实打开 Unity Editor 或未使用 PICO 设备，不得宣称对应运行验证成功。静态检查结果与实际 Play/头显测试分开记录。

## 建议的最小执行顺序

1. `git status`、确定用户提供的交付工程本机路径，做不覆盖原件的副本或可恢复基线。
2. 查看工程入口、`ProjectSettings/ProjectVersion.txt`、`Packages/manifest.json`（若存在）、主要 `.unity` 场景及脚本依赖，检查原有角色/动画/VR 插件。
3. 先按原目录与原版本启动，记录首次错误；优先解决阻止 Play 的几个真实问题。可自行连续修复/回归，不要求形成大量前期审计文档。
4. 在安全公开范围内导入项目，确认提交包含 `Assets/`、`Packages/`、`ProjectSettings/` 和对应 `.meta`；优先不挪动大型素材。如果当前架构较乱，只提出最小后续调整建议，不要求在 P0 整体重构。
5. 查看第一人称场景、人物模型/Avatar、动画、桌面、UI、状态切换和角度驱动各自完成程度；标为“有/部分/无/尚未验证”。
6. 在 Windows Editor 实际运行可用场景；能做则留下截图/日志/操作步骤。无法图形验证时说明障碍，给用户最短的手动操作步骤。
7. 提交 GitHub 工作分支，更新 README/TASKS 和简明记录（例如 `docs/P0-handover-result.md`），附 SHA/可选 PR，列出后续最值得先做的 2–4 项工作。不要伪造测试结论。

## 验收

- GitHub 上有真实 VR 工程的可公开部分，且说明了完整打开方式；原始交付工程可恢复。
- 能在适配版本的 Windows Editor 打开并尽可能 Play 原有场景；如果受环境/依赖限制无法 Play，要有具体阻断和最短用户操作指引。
- 已回答“同学究竟完成了哪些内容、当前运行卡在哪里、接下来如何推进单自由度动作”。
- P0 不要求完成新的全套 VR 游戏、真实空间标定、PICO 构建或 STM32 联调。

**总体原则：先完成再完善，给 Codex 足够尝试空间；每一轮交付能被用户实际观察和复现的进展。**
